# Phase 3C redesign · Baseline-relative Shop learning

This experiment starts from the final 1,000,000-episode Phase 3B-2 Combat and Reward PPO checkpoint. The earlier 200,000-episode ordered-Shop DQN run is classified as a failed experiment and excluded from final performance comparisons. Its source, report and local artifacts are retained. The redesigned run uses a fresh Shop model, fresh examples, its own schema and the default output `data/baseline_relative_shop`. [Historical 200,000-episode report](alternating_rl_200k/README.md) · [Phase 3B-2 reference](combat_rl_1m/training_report.md)

## Alternating experiment

The default budget is 1,000,000 completed episodes in forty blocks of 25,000. The first block trains PPO with the existing uniform shop policy. Odd-numbered blocks after the first train PPO with the learned Shop configuration policy frozen. Even-numbered blocks freeze both PPO heads and update the Shop configuration model. In those blocks, each live Reward decision uses an independent 20% chance to select uniformly from legal reward choices and otherwise samples the frozen PPO policy. Combat remains sampled PPO throughout training. The learner never feeds Reward actions from a Shop block into PPO. Events retain the existing uniform policy.

Combat and Reward still use 583 inputs, seven Combat action logits, five Reward action logits, a shared critic, and the inherited 128/128 architecture. The original masked PPO and per-floor +1 reward remain in use. The loaded checkpoint supplies Adam state and PPO hyperparameters, including learning rate 0.0003, gamma 0.999, lambda 0.95, clipping 0.2, entropy 0.01, minibatches of 256, and four epochs. Shop comparison labels are separate from PPO rewards.

## Counterfactual comparisons at a shop

Every shop reached during a Shop-learning block yields four continuations from the same entry: an immediate exit, and one configuration edited independently by each of Gold, Stats and Skills. Each starts with a full clone of the mutable game and the same simulator RNG state. The four continuations run the same frozen PPO and same Reward exploration mixture. Independent streams for the combat and reward categorical draws, exploration coin, exploration choice and event decision start from the same seed in each branch. Once a configuration changes which random calls or phases occur, alignment is limited to corresponding stream draws. Each comparison is an observed sample with stochastic outcomes.

Branches finish at defeat, the next shop, or the existing late-game milestones. After F90 the horizon is entry to F100 or defeat. After the special F99 shop it is defeat or game clear. A branch reaching the comparison action cap is right-censored. The cap counts continuation actions from departure, excluding edit actions so branches have an equal continuation budget. Fit labels are the sign of the furthest-floor difference, with -1 for loss, 0 for tie, and +1 for win. The signed floor difference is retained separately. Reaching the same floor can yield a tie even when only one branch clears the final boss. Overall evaluation records clears separately.

## Completed configurations

Candidate zero is the unchanged configuration at each stage. The program generates up to eight unique candidates for each applicable head and scores them in a batch. Gold precedes Stats and Skills. Each head sees the live state produced by preceding choices. It receives the choice before that head and the completed configuration, so the learned score can be conditioned on earlier decisions. Independent heads are trained from single-head comparisons. The combined policy can encounter intermediate states outside those training examples, and interaction between purchases and later equipment choices remains an empirical question.

| Head | Proposal process |
|---|---|
| Gold | Sample up to three legal purchases, cost reductions, or at most one deterministic type change. The no-edit proposal preserves all saved gold. A key can create a slot as specified by the game. Reroll is outside the learned proposal catalog because its outcome would be visible to the candidate scorer before execution. The original uniform shop policy can still Reroll. |
| Stats | Allocate a sampled fraction of currently available points, with some proposals first using the original reset. Random weights divide the chosen total. Each stat only increases during the allocation pass after the optional reset. The original +10 and +1 actions and stat menu exit apply the final state. Partial and zero allocation are possible. |
| Skills | Change a sampled subset of unlocked slots at most once, drawing only unused, acquired skills. In a sampled subset of current slots decrease uses by a sampled amount, and in the remaining slots add a sampled amount subject to available mana. Every slot moves in one direction per proposal. The program can keep the original loadout, leave resources unused, and concentrate or spread usage. |

Each completed proposal can be replayed with engine-legal actions. The selected proposal goes through the regular game step API. The simulator continues to enforce purchase order, costs, stat minima, slot availability, acquired skills and mana. No bonuses reward spending, point allocation, memorize counts or individual reward types. The learner encounters each completed proposal once as a training example regardless of how many button presses it took.

## Shop network and data

The input is two ordered 685-feature snapshots, for **1,370 nodes**. Each snapshot has the established 671 features (player 26, six equipment slots × 75, learned skills 88, current costs 88, three mana features, unused stat points, gold, floor, region 11 and event route 2). The 14 additions are base HP, current HP ratio, three base extra stats, four base-type indicators and five flags for purchased shop items. Numerical fields reuse the established scaled encoding and none expose the random generator. The first snapshot is the active head's starting state and the second is its candidate's completed state.

A shared 128/64 tanh encoder feeds three independent linear three-logit outputs for loss, tie and win. Cross-entropy fits the classes, and selection ranks candidates by predicted win probability minus predicted loss probability. The unchanged candidate has exact relative value zero and remains available when estimated benefits are negative. The model starts each head in no-edit mode until that head has received a contrastive minibatch.

The starting Adam rate is 0.001 and the default batch size is 96. Sampling takes equal quotas from available outcome classes within the latest 512 eligible examples per class, per head, under the current frozen PPO version. It waits for at least two observed outcome classes. The aim is to retain useful contrast when labels are sparse. Censored pairs and unmodified proposals are recorded without tensor examples. A modeled score can be biased by class balancing and changing PPO versions. Its calibration and the availability of useful Gold comparisons need empirical checks. The widths bound CPU scoring cost, and the learning rate and batch size are starting settings.

## Evaluation and resource use

At each 25,000-episode boundary and at step zero, evaluation uses the same 128 seed pairs as the Phase 3B-2 panel. It evaluates no-edit shops, each single learned head, and the combined policy on separate copies of that panel with masked argmax PPO and no forced Reward exploration. The initial two evaluation boundaries include the uniform shop reference. Paired episode results compare the policies against the no-edit panel and, when available locally, the original 1M PPO SQLite panel. The historical 200K DQN does not enter the comparison.

The report gives outcome and floor distributions, label mix and mean raw depth difference by head and floor, exit allocations and money, training losses, head timing, and resource snapshots. Reward context includes six HP ratio buckets, distance to the next shop on the current route, and whether the current main or additional stats are below, above, mixed or equal to their base values. Chosen actions are grouped by PPO or forced random source. Mean masked PPO probabilities remain visible in both groups, making very low Gold, Stat or Exchange selection probabilities detectable. The one-edit probes keep the prior loadout and allocations fixed, then apply one legal stat point or Memorize. The unused balance and its matching allocation must change together under the game rules. The probes record predicted score changes and make no claims about outcomes.

The production runtime uses 12 slots across six Windows worker processes, batched CPU PPO inference, reuse of the critic estimates in the rollout, and CUDA parameter updates. Frozen paired continuation inference batches active branch states within each worker using the same weights and action masks. Candidate scoring batches ready shops by head. Branches run synchronously within their worker and can make a long shop visit block progress. Live throughput excludes comparison actions from its action numerator. The report tracks those actions and wall time separately. SQLite commits are batched. It retains outcome telemetry and eligible inputs in FP16 on disk. The learner materializes only bounded class windows and minibatches. Checkpoints contain both models and optimizers, RNGs, active workers, run identity and SQLite watermarks. The latest checkpoint is the resume point. Checkpointing and reporting do not require a network connection.

## Windows commands

- [Start a new run](../run_baseline_shop_rl.bat) uses `baseline_shop/training.json` and the trusted local Phase 3B-2 checkpoint.
- [Resume the same run](../resume_baseline_shop_rl.bat) reloads `latest.pt` with identical settings. A different run needs its own `--output`.
- [Generate the report](../report_baseline_shop_rl.bat) reads the current committed database and writes aggregates under the run's `report/` directory.
- [Validate locally](../validate_baseline_shop_rl.bat) runs a small new experiment in a separate directory and verifies resume and alternation. `--device cpu` runs the same fixture without CUDA.

Each training launcher accepts `--config`, `--output`, and `--initial`. With the default segment length, `run_baseline_shop_rl.bat --stop-at 25000` completes the first boundary and its evaluation before exiting. `resume_baseline_shop_rl.bat` ranges through the remaining budget. An interrupt between checkpoints resumes from the last saved watermark. Experimental outputs, databases and weights stay local.

## Minimum validation and timing

The local CUDA smoke used 48 training games in three segments of 16, four game slots and four fixed-seed evaluation games per mode. It resumed after the first segment and verified all checkpoint watermarks and model freezes. Nine real training shops produced 36 branch continuations with 625 comparison actions, including 27 independent labels: 10 losses, 14 ties and three wins. The Shop interval made seven Stats and eleven Skills updates. Gold had insufficient contrasting examples in this fixture. A unit test verifies Gold learning with legal features and controlled labels, and a separate test compares the CPU counterfactual predictions with the original masked PPO outputs.

During the smoke, Shop-only training took approximately 0.46 s for 16 live games, or 35.1 episodes/s and 2,016 live actions/s. The synchronized comparison call accounted for 0.16 s of that time. The following PPO block with learned Shop configurations processed 22.4 episodes/s and 1,573 actions/s. The first block included CUDA initialization and is not used as a steady-state estimate. These timings and the four-game panels verify functionality. They do not establish sustained throughput or strategic performance for the million-episode experiment.
