# Phase 3B · Reinforcement learning environment design

The objective is to maximize the probability of clearing Dungeon & Rogue 1.00 in Steam. The project target is at least 90%. The proposed first environment uses a Steam-limited observation, a fixed catalog of masked decisions, and a Gymnasium wrapper around the existing simulator. The first learning comparison should use masked PPO with a unified policy and a shared encoder with phase-specific policy heads, with terminal-only reward as the objective reference. This document specifies interfaces and experiments. Model size, training settings, and the production policy remain open.

The design uses the current simulator and the source audit as evidence about game rules and screen availability. Installed Steam build visibility and parity remain unverified. The historical million-game run recorded zero clears, 999,913 defeats, 87 action-limit timeouts, and a maximum floor of 27. Floor 5 was reached by 21.0555% of episodes and floor 20 by 0.0064%. These figures motivate better exploration and depth diagnostics. Skill cohort results reflect survivorship, acquisition opportunities, and interactions with existing builds. They supply no skill bonuses, labels, or priors for the reward. ## 1. Observation specification

Read the relevant screen and any freely accessible information panels before each decision. The simulator adapter should reproduce exactly that information and update a per-run history from visible events and the player's actions. The proposed observation is a fixed-shape Gymnasium `Dict` with phase, run, actors, skills, prompt, history and action mask blocks. Every phase-dependent field has an applicability or known bit. Unknown, inapplicable, known zero, locked slot and empty slot have distinct representations. A missing field carries a neutral numeric placeholder alongside its bit. A last-seen value carries freshness and age, and is separate from a current measurement.

| Block and variables | Availability and semantics | Encoding |
|---|---|---|
| `phase`, `shop_menu`, `floor`, `area`, `gold` | Active screen and HUD. Use an explicit unknown category if the screen does not identify an area. | One-hot phase, shop menu and area. Floor divided by 100. Gold is a nonnegative count. |
| `player`, `enemy` identity and current elemental type | Body names and displayed types, with shared names such as Ella mapped to the same name token. A variant may be distinguished only by visible context. | Public name and type vocabularies. Unknown identity and present flags per actor. |
| Body `hp`, `max_hp`, `attack`, `defense`, `speed`, `EVA`, `ACC`, `DR` | Current HP and current combat stats when visible, including free info panels. A substitute can hide body HP. Preserve a last observed value with age in that case. Infer numerical max HP only from visible base HP, a known full heal, or other verified evidence. Parse omitted enemy fields as zero only when the full panel is known to have loaded and omission means zero. | HP as a scaled count plus HP fraction when the cap is known. Scaled stats, with signed encoding where appropriate. Independent per-field known bits. |
| Body `status_present`, substitute `present` and `hp` | Presence of each visible status icon and visible substitute HP, one block per side. A covered body does not imply no statuses. | Multi-hot status names and a visibility bit. Scaled substitute HP. |
| Player `base_attack`, `base_defense`, `base_hp`, `base_speed`, `available_points`, baseline type and additional stats | Main base stats and allocation points from redistribution. Outside the panel, use known initialization and observed adjustments or a last-seen value. Track baseline type and base EVA, ACC and DR only from visible permanent changes or validated reconstruction. | Scaled numbers, categorical type and per-field freshness. |
| Skill book `learned`, `known_skill_cost` and `cost_reduced` | Learned membership from acquisition and inventory. Track costs from the learned-skill screen and confirmed purchases. Tooltips and public defaults may identify a baseline cost. | Multi-hot learned set in a versioned skill vocabulary. Aligned learned-skill cost values, availability and reduction flags. |
| Six ordered equipped slots and `remaining_uses` | Read the player’s visible slots and current use counters. Preserve ordering and distinguish locked slots. Treat Imitation as a visible equipment change. Track the saved shop allocation from the configuration the player actually left with. | Slot skill token plus lock/presence flags, scaled uses and optional last-observed saved allocation. |
| `max_mana`, `current_mana` | Read the skill management display. Elsewhere expose last seen or a separately marked history estimate if validated. Combat uses and the Ren’Py cached mana balance can diverge. | Scaled counts, current/last-seen flags. A fraction is available when both values are known and the maximum is positive. |
| Reward offer and choices, Ella prompt | Displayed skill or explicit no offer, visible reward options and event choices. The eventual Exchange draw and the eligible reward pool are hidden. | Skill and prompt categories, offer availability and action mask. |
| Shop offers, costs, purchase progress, type targets | Current item offers and prices, shown reroll price, stock and enabled controls. Derive previously purchased items and prior rerolls from confirmed actions. | Per-item availability and price, purchase flags, type-target mask and affordability flags derived from observable balance. |
| Progress and fight history | Track completed fights, actions in the encounter, visited areas, encountered boss names in order and the player's Ella choice. Gate order may be reconstructed only from complete visible history and the rule verified for the installed build. Record the previous player action, announced enemy cast and observed result, including HP and status deltas only where observed. | Bounded counts, ordered categorical tokens and masks. Reset encounter history on an observed new encounter and full history on reset. |

Use `log1p(x / k)` for nonnegative counts with a wide range and `sign(x) * log1p(abs(x) / k)` for signed stats with wide ranges. Choose each positive scale `k` from documented units or training-only calibration, then freeze and version it. Known bounded ratios use linear scaling. Retain enough resolution to distinguish affordability and HP thresholds. Compute rules and masks from raw public values before scaling. Use booleans or compact integer tokens in transport, FP32 for scaled features and one-hot vectors or embeddings at model input. Category IDs are labels without numerical order. Fit any data-dependent preprocessing on training only.

Start with one decision snapshot plus the explicit last-transition and encounter summary. Hidden enemy choices, status countdowns, and scripted changes make the task partially observable. Compare the reference against a short history window or recurrent state if public histories disambiguate relevant outcomes. Feed only events the player could have observed before the current decision. Do not infer a pre-action enemy move from its post-action announcement. Effects whose announcements, duration or visibility are unclear stay unknown pending Steam checks.

### Leakage controls

- Construct observations from an explicit allowlist and a public history tracker. The simulator's raw `get_state()` is a trusted adapter input. Only projected fields, rewards and public masks cross into policy code or training tensors.
- Exclude enemy true IDs, prepared move lists, hidden selected actions and `ram_action`, exact status cure counters, priority and copy flags, Imitation backups, exact shuffled region order, generated Ella loadout, hidden reward candidates, RNG or seed values, and future encounter data. Keep all raw diagnostic payloads in a separate logger. The policy receives no privileged critic input or auxiliary prediction target.
- Build the policy mask from visible controls and validated reconstruction. Compare it against the engine's legal actions in adapter tests. A mismatch requires a documented mapping or a resolved parity issue before that screen enters a Steam-comparable profile. Masking directly from hidden legality can leak information even if no hidden field is present in the observation.
- Test by varying only hidden state or future RNG while holding the visible screen and history fixed. Require identical observation bytes and masks, including in reward, copied-skill, substitute and shop fixtures. Check temporal alignment by changing a later outcome and requiring all earlier observations to stay identical. [Current field classifications](observation_space.md)

## 2. Action specification

Use `Discrete(N)` over a versioned catalog of complete action descriptors. A Boolean mask of length `N` accompanies each decision. Use stable, explicit public skill and item vocabularies, reserve invalid and padding cases through masks, and decode slot references to the currently shown equipped skill before calling `Game.step()`. The following inventory covers the current engine's decisions. Exact costs, step sizes and ordering come from the pinned data. [Game action API](../simulator/game.py) · [Rewards](../simulator/rewards.py) · [Shop](../simulator/shop.py) · [Configuration](../data/game_config.json)

| Phase | Catalog action and simulator translation | Enabled when |
|---|---|---|
| Combat | Cast slot 1–6 → `skill(name)` | Slot is unlocked and uses are positive. The button can remain legal when a later execution check skips the cast. |
| Combat | Sacrifice → `skill(sacrifice)` | Every equipped unlocked skill has exactly zero uses. |
| Reward | `reward(Gold)`, `reward(Potion)`, `reward(Initialize)`, `reward(Stat)`, `reward(Exchange)` | At the reward prompt, all five are valid, including Exchange with no offered skill. Gold adds gold, Potion heals, Initialize resets volatile stats and statuses, and Stat draws an additional-stat upgrade. The chosen or redrawn offer is learned automatically if present. Exchange can redraw the same skill. There is no separate accept, reject or choice among hidden skills. |
| Event | `ella(pickpocket)` or `ella(help)` | Floor-35 Ella decision prompt. The scripted later route remains engine-controlled. |
| Shop main | `shop_menu(skills/costs/stats/merchandise)`, `leave_shop()` | At shop main. Leaving saves the allocation and advances to the next area. |
| Skill setup | Increase uses → `memorize(name)`. Decrease uses → `forget(name)` | An unlocked equipped slot and enough available mana at that slot's current cost, or at least one allocated use for a decrease. Decreasing uses returns allocation capacity and preserves the learned and equipped skill. |
| Skill setup | Replace `slot, new_skill` → `replace_skill(old, new)` | The slot is unlocked and the replacement is learned and unequipped. Replacement starts with zero uses and releases the old allocation. The Steam adapter should map the compound decision to the two source clicks. |
| Cost reduction | `reduce_skill_cost(name)` | Learned skill, enough gold, still at its original cost and at least the minimum cost after the one allowed reduction. |
| Stat redistribution | `adjust_stat(stat, delta)` for ATK, DEF, HP, SPD and ±1, ±10. `reset_redistribution()` | In redistribution, with enough points for an increase or a resulting base value of at least 1 for a decrease. Reset is offered in that screen. |
| Merchandise | `reroll()` | Gold covers the current cost and base EVA + ACC + DR meets the minimum. Simulator rerolls redistribute the total and double the price. Verify the installed build given the source issue in F-06. |
| Merchandise | `buy(blue_key/red_key)` and `buy(blue_mana_potion/elemental_mana_potion/undead_mana_potion)` | Only the first unpurchased item in each group, when affordable. Keys also require a locked slot. An eligible key purchase can still charge gold when no unequipped skill can fill that slot. |
| Merchandise | `change_type(Undead/Elemental/Beast)` | Gold covers the cost, current type is non-Normal, and target differs from both current and baseline type. |
| Shop submenu | `shop_back()` | In any submenu. Confirming redistribution applies stat reset and recovery as part of returning. |

The adapter handles Start as `reset`, bundles free information panels with observation acquisition, and leaves settings, save/load, cosmetic navigation and replacement cancellation outside the run decision catalog. The source and engine offer no combat wait, flee, manual area choice or permanent skill removal. Keep state-consuming actions even when their outcome could be empty, such as Exchange with no candidates. A disabled click or menu-only cancel is a UI interaction with no competing strategic transition. [Action availability and interface differences](simulator_fidelity.md)

With `M` entries in a frozen catalog of learnable skills, this layout uses `N = 58 + 7M` IDs. The parameterized blocks cover six replacement slots per skill and one cost reduction per skill. Generate IDs by the table's block order and explicit parameter orders, and persist the mapping with the schema version. Sacrifice has a dedicated combat ID. It is outside the learnable vocabulary.

| Representation | Advantages | Trade-offs |
|---|---|---|
| Fixed flat masked IDs | One Gymnasium space, stable replay and logging, simple batched inference and uniform sampling. Exact slot-and-target masks preserve valid pairs. | Sparse logits outside the active phase, with replacement alone requiring up to six times the size of the replacement vocabulary. Calculate `N` from the persisted catalog. |
| Phase-specific action spaces | Smaller heads, easier per-phase entropy diagnostics and fewer inactive scores. | A changing public action space complicates vector batches, replay and policy APIs. Keep the fixed public IDs and route internally through phase heads if this variant is selected. |
| Conditional slot and replacement selection | Avoids scoring every pair and shares structure across skills. | The replacement mask must depend on the chosen slot. Sum conditional log probabilities for PPO and preserve one step per complete pair. Independent masks can admit invalid combinations. |

Sample or maximize over valid actions only. Mask behavior sampling, evaluation, PPO log probabilities and entropy, and DQN next-state targets. Store the exact mask used by the behavior policy. Reject invalid IDs before engine execution and log the integration error separately. A nonterminal empty mask is an adapter failure. A terminal observation may have an all-false mask and must never be sampled. Uniform Random Policy draws uniformly over complete legal actions. Sampling uniformly over action types or each component would change the baseline distribution.

## 3. Reward candidates

The selection metric is undiscounted clear probability per started run. The clean training reference pays `+1` on clear and `0` otherwise. An explicit death penalty can be tested separately. With complete episodes and the same penalty for all genuine failure outcomes, clear and failure rewards can be equivalent up to an affine change in undiscounted return. Discounting, censoring and differing penalties break that equivalence. A nontrivial discount also favors faster clears even if both policies have the same clear rate.

| Candidate | Definition | Main trade-off and failure mode |
|---|---|---|
| A. Terminal-only | `+1` for clear, zero for death and other outcomes. Compare a symmetric clear/failure variant separately under a declared terminal convention. | Direct objective and easy audit. Sparse successes are expected given baseline depth. Penalizing death more than timeouts can teach stalling. |
| B. Potential shaping | Add `γΦ(x_next) − Φ(x_now)` using the same discount as the return. Start with bounded visible progression as the potential. Compare a second potential containing bounded HP and spendable resource terms. | Offers a learning signal between terminal events. Use zero potential at task terminals and consistent continuation at budget cutoffs. Naively zeroing the potential at an external truncation introduces a boundary reward. Partial observability and finite rollouts require empirical comparisons. |
| C. One-time milestones | Add bounded bonuses for the first time a floor is reached and optionally a verified boss defeat. Use an episode ledger keyed by observed encounter milestone, with handling for multiple fights on floor 99. | Gives early exploration a signal, but farming or optimizing safe lower-floor milestones can beat risky clear attempts under the shaped objective. Avoid paying independently for a kill and its floor advance by default. |
| D. Resource and repetition ablations | Keep HP survival margin, gold, mana, remaining casts, skill-slot coverage and repeated actions as metrics first. If tested as reward, use a bounded potential or a narrowly scoped cost for proven no-progress cycles. | Raw positive HP, purchases, casts, or loadout changes can reward healing loops, unnecessary spending, and swapping back and forth. Counting repeated actions can punish correct repeated attacks or forced Counter. Costs can favor quick deaths or skipping useful setup. |

Potential shaping telescopes given consistent discounting and boundary treatment. Benchmark it against A under the same evaluation protocol. Avoid fixed skill quality bonuses, such as giving points for acquiring a skill associated with higher floors in the random cohort. Use skill composition as observed policy input and a stratified diagnostic. Choose reward candidates by validation clear rate, with floor survival and stall rate as supporting metrics. [Ng, Harada and Russell, Policy Invariance Under Reward Transformations](https://people.eecs.berkeley.edu/~pabbeel/cs287-fa09/readings/NgHaradaRussell-shaping-ICML1999.pdf)

### Unwinnable states and time limits

Maintain a faithful evaluation profile with the historical 10,000-action cap. A verified Counter–Mimic lock is annotated but remains subject to that cap for direct baseline comparisons. For efficient training, consider a separate profile that truncates early on the proven absorbing pattern. Detection needs the full validated preconditions and observable persistence, including only Counter available, a faster player, Mimic's refusal and no ongoing effect that can change legality, speed or HP. Repeated snapshots alone are insufficient. Ordinary reversible shop cycles and stochastic misses use the normal cap.

Early deadlock stopping gives zero clear credit and logs `deadlock_mimic_counter` separately from death and ordinary `action_limit`. It must never grant a positive reward merely for ending early. A true deadlock has no future clear reward under the engine, so an optional learner-side absorbing-failure target can assign zero continuation value to the **unshaped** value component. For shaped returns apply the corresponding remaining potential boundary consistently. Validate those targets separately from generic time-limit bootstrapping. No action or recovery branch is injected into combat. [Mimic timeout investigation](mimic_timeout_analysis.md)

## 4. Environment architecture

Keep the core `Game` and RNG behavior as the transition authority. Place the environment contract in a separate package that owns observation projection, public history, action translation, reward calculation and episode limits. The same public schema is the future interface for a Steam adapter. The simulator has no dependency on Gymnasium, PyTorch, GPU state or the learning policy. One environment step is one accepted engine decision, including rewards and shop navigation. Free observations and automatic combat or dungeon transitions add no steps.

| API | Design |
|---|---|
| `reset(seed=None, options=None)` | Initialize Gymnasium's generator via `super().reset(seed=seed)` and reset the per-run tracker and counters. Derive the simulator episode seed from the wrapper generator or consume the explicit manifest seed under the documented convention. Return `(observation, info)` including its mask in the observation. `seed=None` continues the wrapper's RNG stream. |
| `step(action)` | Decode and validate the fixed ID, invoke `Game.step()` once, observe public transitions, compute reward and return `(observation, reward, terminated, truncated, info)`. Contract errors are recorded separately and surfaced. |
| `terminated` | `True` on a game clear or game-over death. Return the final observation when either occurs. |
| `truncated` | `True` on a valid external action limit or optional proved early deadlock cut. A game terminal on the last permitted action takes precedence. Worker crashes and malformed actions are errors, not standard truncations. |
| `info` and metrics | Use an outcome code, reason, step counts and aggregate diagnostics for evaluation. The policy reads only its declared observation and mask. Keep run IDs and seeds in a separate experiment log. Preserve the final observation and mask across autoreset for value targets. |

At a true game terminal, the learner does not bootstrap. At an ordinary external cutoff, a continuation-value method bootstraps from the final pre-reset observation. Reset recurrent state across any actual reset. Explicitly select and test vector autoreset behavior. [Gymnasium Env API](https://gymnasium.farama.org/api/env/) · [Gymnasium vector API](https://gymnasium.farama.org/api/vector/) · [Farama autoreset modes](https://farama.org/Vector-Autoreset-Mode)

Use a logged master seed and deterministic domain-separated streams for split, episode index, policy sampling, model initialization and processing order. Allocate immutable episode IDs independently of worker scheduling. The engine derives its own independent reroll stream from the supplied game seed, so no extra wrapper RNG draw should enter game transitions. Record dataset, simulator, schema and reward revisions, seed derivation version and full seed manifests. Check that equal seeds and action sequences yield equal results across worker counts. Parallel GPU training reproducibility requires separate measurement and recorded runtime settings.

Begin with a single-process reference. Then use Windows `spawn` CPU workers, each loading immutable game data once and owning its environment state. Use Gymnasium vector environments or a bounded worker transport with an identical contract. Project features and masks before serialization. Store rollout batches as fixed-shape arrays in shared memory where supported and use a central process for batched CPU or GPU inference and updates. Reuse buffers, consider pinned transfers only if measured, and pass selected action IDs back to workers. Keep validation separate from training state and prevent stale on-policy batches from mixing incompatible policy versions. Benchmark packed observation and mask bytes, collection, queue wait, transfer, inference, update, RAM and VRAM during sustained runs.

The local RTX 5070 Laptop GPU has about 8 GiB VRAM and the system has 32 GiB RAM. The existing synthetic combined benchmark measured a median 52,841 steps/s at 12 workers. Start the pipeline benchmark with 12 workers and one learner, checking fewer workers and the 16-worker case. The measured throughput used synthetic batches and random actions. Real inference latency, action-mask size, phase imbalance and queue synchronization can alter the best worker count. Bound rollout and replay memory before scaling, and compare CPU inference for small batches. [Local hardware benchmark](hardware_benchmark.md)

## 5. Learning architecture candidates

| Architecture | Fit for this game | Principal cost |
|---|---|---|
| Unified network | A shared policy and value representation sees combat, rewards and shop decisions and can credit long-term build choices. Provides a straightforward masked PPO reference. | Combat dominates the sample mix. A flat output scores many inactive IDs and may underfit rare situations. |
| Shared encoder, phase-specific heads | Shares HP and resource representations across decisions while giving combat, rewards, shops and events separate output capacity. A shared value function can still estimate whole-run return. | Rare heads receive few updates. Batching by mixed phases, phase-aware diagnostics and stable mapping back to public IDs are required. |
| Independent networks | Useful for isolating performance of a combat policy or a shop policy with the other policies fixed. | Multiple independently updated policies change each other's future state distributions. Credit assignment and memory costs grow, and early shop sample counts are low. |
| Hierarchical RL | Multi-step options could represent completing shop setup or pursuing a resource objective across fights. | Option design, duration and termination complicate attribution and may exclude valid tactics. Require evidence of a bottleneck from simpler phase-aware policies first. |

**Masked PPO** is the recommended first algorithm candidate because valid actions change each step, one on-policy rollout can capture both shop and fight decisions, and a shared critic can connect spending to future survival. Its on-policy collection is demanding with sparse successes, so report sample budget and wall time. Compare a unified head with phase-specific heads under the same interface and matched experiment budgets. A recurrent encoder is an ablation for partial observability. [PPO paper](https://arxiv.org/abs/1707.06347)

**Masked DQN** is an off-policy comparison with replay reuse and a discrete action catalog. Apply valid-action masks to exploration, greedy selection and target maximization. Retain next-state masks in replay. A flat action head can be wasteful for replacement pairs, and small replay buffers can lose rare shop or deep-floor transitions. If using prioritized or sequence replay, account for sampling bias and RAM use. Deep returns, stochastic action outcomes and partial observability can make value targets unstable. DQN and PPO comparisons should share the same observation, cap and evaluation panels. [DQN paper](https://arxiv.org/abs/1312.5602)

## 6. Evaluation protocol

1. Pre-register disjoint training, validation and locked test seed manifests. Use validation for reward, model and checkpoint selection. Keep the final test panel independent of those decisions. Run multiple independent training seeds. On paired evaluation panels, use identical game seeds across policies and logged independent policy seeds for stochastic policies. Fix whether evaluation is greedy or sampled in advance and report each separately if both are tested. Different actions may consume the engine RNG differently even on matched seeds.
2. Re-run Uniform Random Policy on the shared evaluation panel under the same schema, action semantics and cap. Compare against the historical million as an anchor. Use the original engine legal-action order for exact historical seed replay and uniform complete-action sampling for the new panel. Add Greedy and Heuristic baselines later under the same public inputs and reporting rules. Log any differences in navigation or action accounting.
3. Report clears divided by all valid started evaluation games as the primary simulator estimate. Timeouts and proven deadlocks count as non-clears and have separate counts. Report errors and coverage explicitly. Predefine retries for infrastructure failures on the same seeds, retain unresolved errors and give the all-attempts clear rate with unresolved runs counted as non-clears as a conservative sensitivity check. Report mean and median furthest floor and `P(reached floor ≥ f)` over the same denominator. Show conditional per-floor progression, deaths and censoring separately for diagnosis, with counts and floor-99 encounter detail where relevant.
4. Record cumulative accepted environment steps, completed and started episodes, learned updates, actual elapsed time, evaluation time and worker counts. Plot clear rate and floor-depth metrics against training steps and wall time. Use fixed checkpoint schedules and distinguish training statistics from independent evaluation. Compare policies both at matched step budgets and matched time budgets.
5. Report 95% binomial intervals, such as Wilson, for fixed-policy clear rates and per-floor reaches. For paired policy differences, resample paired game-seed records. Across independently trained models show per-run estimates and uncertainty across training seeds. Freeze test size before viewing results and choose it for the desired precision near 90%. A zero-clear sample still has a nonzero upper confidence bound. Report all outcomes together with the intervals.
6. Confirm the 90% target separately using fresh Steam runs with a locked policy, no reloads and the same outcome definitions. Report the build, observation coverage, failures and confidence interval. If the claim requires evidence that the underlying clear rate is at least 90%, predeclare a one-sided confidence criterion as well as the number of attempts. Simulator estimates do not establish the Steam result.
